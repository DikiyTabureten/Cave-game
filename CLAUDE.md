# Cave Game — инструкции для Claude Code

Этот файл читается в начале каждой сессии. Здесь описаны проект, правила работы и способ проверки результата.

## О проекте

**Cave Game** — небольшая обучающая игра-тренажёр по вязке туристических и спелеологических узлов.

- **Аудитория:** подростки 12–18 лет, туристические и спелеоклубы.
- **Распространение:** бесплатно, некоммерческий образовательный продукт. Никакой монетизации внутри игры.
- **Платформа прототипа:** ПК (мышь), сборка **WebGL**. Позже Android (тач). Код с первого дня пишем так, чтобы он работал в WebGL и с тачем.
- **Формат:** в духе Duolingo — короткие уровни, понятный прогресс, мгновенная обратная связь.

### Сеттинг и стиль (на будущее, не для первого прототипа)

- Тёмный мир пещеры: карта, свет налобного фонаря.
- Учебный контент — страницы полевого блокнота, освещённые фонарём.
- Прогрессия — спуск по уровням пещеры.
- Маскот-наставник — летучая мышь. После каждого узла — короткая карточка-факт.
- Пиксель-арт **не используем**: для вязки узлов он не подходит.

## Что строим сейчас

**Только прототип механики вязки узла.** Сеттинг, карта, маскот и меню — потом.

### Core-механика: пошаговая вязка

- Игрок ведёт конец верёвки мышью (позже пальцем) по заранее заданному пути узла, шаг за шагом.
- Путь узла — набор точек и шагов в данных, а не расстановка в сцене.
- Вид сверху, 2D. Верёвка рисуется через `LineRenderer` (или сплайн). **Физику верёвки не делаем.**
- Если конец ушёл с пути, отклонение подсвечивается (красным), шаг не засчитывается.
- Когда пройден последний шаг, появляется экран «Узел завязан».
- Верёвка проходит над и под собой: порядок слоёв в точках пересечения задаётся в данных.

### Узлы прототипа

Начинаем с **одного узла: «восьмёрка»**. Следующие добавляем только после того, как первый проходится от начала до конца. Кандидаты: проводник-восьмёрка, булинь, прямой, штык. Список уточняет пользователь.

## Технический стек

- **Unity 6000.2.13f1** (Unity 6.2).
- **URP, 2D-проект** (2D Renderer). Камера ортографическая, всё в плоскости XY.
  - Верёвка — `LineRenderer` (или `SpriteShape`), порядок отрисовки через Sorting Layers / Order in Layer.
  - Перехлёсты «над/под» — разбивай верёвку на сегменты с разным `sortingOrder` в точках пересечения.
  - Свет налобного фонаря позже делаем через `Light2D` (URP 2D Lights). В прототипе освещение не нужно, но не ломай 2D Renderer.
- Input System **проверь сам** (Project Settings → Player → Active Input Handling). Не меняй пайплайн и ввод без спроса.
- Unity MCP (MCP for Unity) подключён: им можно создавать объекты, читать консоль и запускать тесты в открытом редакторе.
- Git, удалённый репозиторий на GitHub. Пользователь смотрит изменения в GitKraken.

## Структура проекта

```
Assets/_Project/
  Scripts/Runtime/    CaveGame.Runtime.asmdef   — игровая логика и представление
  Scripts/Editor/     CaveGame.Editor.asmdef    — editor-скрипты (генерация сцены, данных)
  Tests/EditMode/     CaveGame.Tests.asmdef     — тесты логики
  Data/Knots/         ScriptableObject с описанием узлов
  Scenes/
  Prefabs/
  Materials/
```

Всё своё кладём только в `Assets/_Project/`. Сторонние пакеты не трогаем.

## Архитектурные правила

- **Логика отдельно от представления.** Проверка шагов, попадание в путь и состояние узла — в чистых C#-классах без `MonoBehaviour`, чтобы их можно было тестировать в EditMode. `MonoBehaviour` только связывают логику с вводом и отрисовкой.
- **Сцена собирается кодом.** Либо Bootstrap-скрипт создаёт объекты на старте, либо editor-скрипт генерирует сцену и префабы. Минимум ручных настроек в инспекторе.
- **Данные узлов — в ScriptableObject** (`KnotDefinition`: название, список шагов, точки пути, допуск отклонения, слои пересечений).
- **Совместимость с WebGL:** никаких потоков (`System.Threading`), `System.IO` во время игры и нативных плагинов.
- **Ввод через абстракцию:** «указатель нажат / двигается / отпущен», чтобы потом без переделок добавить тач.
- **Графика — заглушки:** примитивы, `LineRenderer`, простые цвета. Красоту добавит пользователь.
- Текст в UI — на русском.

## Как проверять работу (обязательно)

После **каждого** изменения кода:

1. Дождись перекомпиляции и **прочитай консоль Unity через MCP**. Ошибок компиляции быть не должно. Пока консоль не чистая, к следующему шагу не переходи.
2. **Прогони EditMode-тесты** через MCP. Все должны быть зелёными.
3. Для новой логики **сначала пиши тест**, потом реализацию.

Если MCP недоступен, запускай тесты в batchmode. Проект при этом должен быть закрыт в редакторе. Путь к Unity.exe уточни; вероятно, это `C:\Program Files\Unity 6000.2.13f1\Editor\Unity.exe` или `C:\Program Files\Unity\Hub\Editor\6000.2.13f1\Editor\Unity.exe`:

```
"<путь к Unity.exe>" -batchmode -nographics -projectPath . -runTests -testPlatform EditMode -testResults TestResults.xml -logFile -
```

Ощущения от механики (приятно ли тянуть верёвку) проверяет пользователь в Play Mode. В конце задачи коротко напиши, что именно стоит проверить руками.

## Git

- Работай в ветке **`claude-dev`**. В `main` не коммить.
- Коммить мелкими рабочими шагами, после зелёных тестов. Сообщения — на русском, кратко, по делу.
- **`git push` не делай**: пушит пользователь.
- Не коммить `Library/`, `Temp/`, `Logs/`, `obj/`, `UserSettings/`, `Builds/`. Проверь `.gitignore`.
- Asset Serialization = Force Text, мета-файлы видимые. Каждый новый ассет коммить вместе с его `.meta`.

## Что нельзя без спроса

- Менять `ProjectSettings/`: рендер-пайплайн, Input System, Player Settings.
- Устанавливать или удалять пакеты.
- Удалять файлы вне `Assets/_Project/`.
- Делать `git push`, `reset --hard`, `rebase`, переписывать историю.

## Определение «готово» для задачи

- Консоль Unity без ошибок.
- Все EditMode-тесты зелёные.
- Изменения закоммичены в `claude-dev`.
- В ответе: что сделано, что проверить руками в Play Mode, какие решения остались за пользователем.
